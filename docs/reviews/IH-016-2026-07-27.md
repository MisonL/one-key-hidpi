# IH-016 Verification Record

## Scope

This task strengthens rollback authorization after a reboot or a same-content
file replacement. It changes the Intel safe apply/revert implementation only.
All automated writes were confined to `mktemp` fixture roots.

No command in this task rebooted the host, slept or woke the host, hot-plugged
a display, reloaded a display service, or wrote a real display override.

## Implemented Boundary

- Manifest version 5 records the current boot session and persistent file
  identities in the form `inode:birthtime-seconds:birthtime-nanoseconds` for
  the installed candidate and, where applicable, the exact original backup.
- Apply snapshots the original override with hash, device/inode, and persistent
  identity. Secure copy, install, replace, restore, and removal helpers retain
  that identity check at their write or cleanup boundary, including final
  manifest cleanup.
- Revert permits a changed device number after a boot only when the hash and
  persistent identity still match. In the same boot session it additionally
  requires the recorded device/inode identity.
- A v4 manifest never silently uses the weaker identity rule. Revert requires
  `--migrate-v4`, verifies the legacy target and backup first, atomically
  writes a verified v5 manifest, then continues only from the migrated state.
- A v5 target replaced with equal bytes but a different persistent identity is
  retained instead of being overwritten.

## Remaining Boundary

Persistent identity narrows accidental or unprivileged same-content replacement
races. It cannot make a rollback transaction immune to an attacker who can
modify the protected system override tree and the root-owned state tree with
equivalent privileges. Such a process can still race separate filesystem calls;
the implementation fails closed and retains state when its checks fail.

## Complexity Exemption

`commit_apply_state` and `revert_override` remain cohesive transaction
boundaries despite their size and parameter count. Splitting their state across
helpers would increase mutable security context and make lock, temporary-file,
and failure-retention ordering harder to audit. Their phase boundaries are
covered by the dedicated fixture suites and this review record documents the
exception for IH-016.

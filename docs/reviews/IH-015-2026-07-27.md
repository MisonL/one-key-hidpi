# IH-015 Verification Record

## Scope

This task closes the legacy recovery helper's current-directory and broad
deletion boundary. It changes only the generated `.hidpi-disable` helper and
the legacy menu's disable choice. It does not change the Intel safe
apply/revert implementation.

No command in this task used `sudo`, wrote `/Library/Displays`, wrote
`/Library/Application Support`, changed a real display configuration, or
created a real system override. All writes were confined to `mktemp` fixture
directories.

## Implemented Boundary

- `legacy_recovery_volume_root_from_script` derives the volume root from the
  executing helper's `BASH_SOURCE`, rather than the process current directory.
  It accepts only a regular `.hidpi-disable` file under
  `<volume>/Users/<user>/`, rejects symbolic links and hard links, and compares
  the original and canonical device/inode/link-count identities before use.
- The generated helper validates that root before display detection. Symbolic
  links, hard links, and non-standard locations exit explicitly and do not
  print success. A standalone copy or move in another valid
  `<volume>/Users/<user>/` layout is bound to that other volume rather than
  the process current directory.
- The generated helper now invokes display discovery only after the path trust
  check and builds `restorePath` from the validated volume root.
- Both legacy entry points expose only choice `1`. The former reset-all choice
  and its recursive deletion of the whole Overrides root are removed.
- Existing per-product cleanup remains fail-closed: preflight validates the
  vendor and `Icons.plist` paths before mutation; any precise unlink or plist
  edit failure exits before `HIDPI Disabled` is printed.

## Regression Coverage

`tests/test_intel_hidpi_legacy_cleanup.sh` verifies all paths in isolated
temporary volumes:

- a recovery helper run directly from a decoy working directory removes only
  the selected product from its own volume and preserves both same-vendor
  siblings and the current-directory decoy;
- hard-linked, symbolic-linked, and non-standard helper locations are rejected
  before cleanup, preserving their selected target and sibling; a standalone
  copy under a second valid volume layout affects only that second volume;
- choice `2` is rejected by both the legacy menu and the generated helper,
  with no success message and no deletion;
- a product entry represented by a directory makes the precise unlink fail,
  preserving the directory and sibling and preventing the success message;
- existing `Icons.plist`, vendor-link, attachment-link, hard-link, and
  replacement-race cases remain rejected or constrained to the selected
  product as appropriate.

The helper source is also inspected by the test: it contains no legacy
`rootPath="../.."` calculation and no `rm -rf`; the source contains neither
the removed reset command nor the removed menu label.

## Self Review and Remaining Boundary

- `git diff --check` passes and the task diff is limited to the recovery
  implementation, its focused regression fixture, two recovery instructions,
  this record, and the IH-015 task state.
- The deletion path remains product-scoped to `DisplayProductID-<id>`,
  `.icns`, and `.tiff`; it intentionally leaves an empty vendor directory,
  avoiding pathname-only directory deletion races.
- A non-cooperative process with permission to modify the helper's parent
  directory or the protected system Overrides tree can still race operations
  across separate system calls. The implementation binds the helper identity
  before use, uses descriptor-bound `openat` and `O_NOFOLLOW` for cleanup, and
  fails closed when a checked path is unsafe, but this cannot be represented as
  an absolute transaction over an attacker with equivalent system privileges.
- IH-005 remains unstarted. Real Intel external-display enablement, reboot,
  sleep, hot-plug, and rollback require explicit user authorization and were
  not attempted.
